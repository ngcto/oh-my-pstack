### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your independent root verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** GitHub via `gh` is the only forge. Set the program's done predicate once with `/goal` so it survives compaction. One `poteto-agent` per PR, spawned through the `task` tool with `isolated: true` so it works in its own worktree, on the `code` role model. Isolation needs `task.isolation.enabled` and has a fallback when it is off, both in poteto-mode's Subagents section. The owner publishes through its pushed branch and its PR, and the PR is the deliverable, not the worktree. With `task.isolation.apply` on (the default), OMP applies a successful owner's changes to the root checkout on its own, so set it to false before the program starts (the `setup-pstack` skill offers that) or treat the root checkout as scratch, review `git diff` there, and never commit it. The owner owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical review-bot triage per `references/review-bot-triage.md`, a slop-strip (the `deslop` skill), the `no-comments` skill when changed comments need independent cleanup, review chosen or reused under `skill://thermos`, a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after applicable cleanup and any chosen review, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with any required verification lanes. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Run the pre-review checks that the repo's AGENTS.md files and rules require for the touched paths on the committed head. Reuse unaffected receipts under step 4. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private stack of its own, per the `stacked-prs` skill. That owner is the only stacker for that stack, so it alone runs `gh stack` mutating commands on it, and it lands the stack bottom-up with `gh stack merge <pr> --yes` only after step 4 passes for every layer at or below `<pr>`.
4. **Give each PR an independent root verdict before merge.** At the code-ready head, inspect the owner's receipts and remaining uncertainty. Record the exact head SHA, base SHA, and stable patch-id with the verdict. Reuse a valid independent audit or GitHub review together with existing self-proof and CI receipts. Use `skill://thermos` for review choice, reuse, and stopping. Autonomous execution does not raise the review level. For a small low-risk unit, a direct check and receipt is enough. The root judges that evidence without spawning a review-only agent to rerun a command. Behavioral work still needs a relevant live check on the real surface with the matching control skill, such as `control-cli` or `control-ui`, or a named driver where none exists. When a regression comparison is relevant, run the same load-bearing scenario on current trunk and head. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. Use `skill://blast-radius` inline to investigate one or two named uncertainties before selecting swarm coverage or a deeper review under `skill://thermos`. Use `skill://swarm` for distinct scenarios that need parallel coverage. When the review policy selects thermos, it replaces duplicate diff-audit lanes rather than running beside them. Pass a scope spec for any chosen diff review, with the base ref, head SHA, PR number, and intent paragraph, not a pasted diff. Review never replaces behavioral proof. Audit the merge-ready receipts before recording the root's passing verdict under the blocker and stop rules in `skill://thermos`. P2 and P3 suggestions may remain. Send confirmed in-scope blockers to the owner together. For an accepted behavior defect, get a regression test at the owner boundary that fails for that defect, or a repro receipt when no test can show it. Verify accepted fixes on the affected path. For each later head, apply the patch-id rule in `playbooks/shipping.md`, refresh only affected checks or lanes, and record the current-head verdict with the evidence retained or refreshed. A new SHA, push, rebase, or review round does not itself trigger a fresh swarm or local review. Any further review follows `skill://thermos`. Scope a newly introduced risk to its delta. No merge without the root's passing verdict.
5. **On a passing verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep follows the root's initial receipt check, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the verdict's evidence still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `playbooks/shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. Record a verdict for the current head under step 4, carrying forward valid evidence and refreshing only affected checks or lanes. The owner squash-merges its own PR with `gh pr merge <pr> --squash` and returns. An owner holding a private stack (step 3) is its own single stacker, so it does merge prep with `gh stack rebase` then `gh stack push`, and lands with `gh stack merge <pr> --yes --squash` on the highest PR of the contiguous verified run, never `gh pr merge`, since a stacked PR cannot land alone. It re-reads the target PR's head SHA right before that merge and compares it with the verified SHA, per `playbooks/shipping.md` step 5. A fresh owner picks up the next self-contained item from the queue, per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's passing verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. The tick clock is an async `bash` job that runs `sleep 3600` (`async: true`, no `name`, `timeout: 0`), started on the operator's go and restarted as the last act of every tick. Its completion is delivered to you as a follow-up and wakes the session, so the running job is the cadence. `/loop` is a command the user types and no tool starts it, and its duration is a total budget rather than an interval, so it is not this clock. An operator who wants a driver that outlives the session starts `/loop --until '<done command>' <tick prompt>` themselves. Never leave the cadence to memory, and never depend on an owner's completion notification arriving. At each tick, re-read this playbook with `read skill://poteto-mode/playbooks/autopilot-full.md` and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check (its `agent://<id>` status or the agent hub), and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list in the agent hub and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge review-bot comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict with its exact-head receipts and the checks, lanes, or reviews run or reused. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
