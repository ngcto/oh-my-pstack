### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear GitHub stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** GitHub via `gh` is the only forge. The stack is a native GitHub stacked-PR chain per the `stacked-prs` skill. If `gh stack` is missing, or the availability probe `gh api -H 'X-GitHub-Api-Version: 2026-03-10' "repos/<owner>/<repo>/stacks" --silent` returns 404 (stacked PRs not enabled on the repo), say so once and fall back to the `stacked-prs` skill's plain-PR fallback. Exit 9 only comes from `submit`, `merge`, `link`, and `checkout`, so it confirms a 404 but never replaces the probe. Set the program's done predicate once with `/goal`. One `poteto-agent` per PR, spawned through the `task` tool with `isolated: true` on the `code` role model (isolation setup and its fallback are in poteto-mode's Subagents section), owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical review-bot triage per `references/review-bot-triage.md`, a slop-strip (the `deslop` skill), the `no-comments` skill, a `thermos` pass on its scoped diff, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on a real clock.** The root runs an audit tick every hour, driven by the async `sleep 3600` job of Autopilot-full step 6, started on the operator's go and restarted at the end of every tick. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook with `read skill://poteto-mode/playbooks/autopilot-stack.md` and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all subagents and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. That means swarm lanes plus the two thermos lanes on the PR's own diff, and a clean verdict needs both thermos lenses free of P0 and P1. For a stack layer, the thermos scope is that layer alone: `git diff <parent-branch>...<branch>`, with the layers below named for context. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges or closes, and nothing is queued for merge. A clean verdict appends the PR to the one linear stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners commit and push only their own layer branch and report the tip, current base, and intended parent. They never rebase and never run `gh stack` mutating commands (`init`, `add`, `rebase`, `sync`, `push`, `submit`, `link`, `unstack`, `merge`). The root is the one stacker, the only writer of stack topology, and records that in the standing orders. To append a PR, the root checks out the stack with `gh stack checkout <target>` or runs `gh stack init <branch>...` for a new one, runs `gh stack top` so it stands on the top branch (`gh stack add` only works there), brings the owner's branch in as the next layer (`gh stack add <branch>` with the name explicit, or `gh stack init` over existing branches, which adopts them), runs `gh stack rebase` then `gh stack push` so every layer sits on current trunk (`submit` does not rebase), and runs `gh stack submit --auto --open`, which pushes, opens ready PRs, and sets each base to the branch below. `submit --auto` titles each PR from the commit subject or the humanized branch name and leaves the body empty, so right after it the root runs `gh pr edit <n> --title "<Conventional Commits title>" --body-file <file>` on every new PR, with the title and description written per **Titles** and **Descriptions** in `playbooks/opening-a-pr.md`. Only the bottom PR targets trunk. Never hand-retarget with `gh pr edit --base` inside a stack. Read state with `gh stack view --json`, never bare `view`, and never use `switch` or `modify`.
7. **Absorb drift at the root, then re-verify what moved.** The root runs `gh stack sync` to fetch trunk, rebase the chain bottom to top, push, and refresh PR state. Bare `gh stack sync` prompts on a TTY (prune, divergence), so pass `--prune` only when pruning merged branches is wanted and treat any other call as able to hang in an agent run. When non-interactive certainty matters, use `gh stack rebase` then `gh stack push` instead. On exit 3 (rebase conflict), `sync` has already restored every branch and there is no rebase in progress, so `--continue` is wrong at that point. The root runs `gh stack rebase`, which stops at the conflict. The owner of the conflicting layer fixes its own slice, and the root finishes with `gh stack rebase --continue` and `gh stack push`. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. Recompute the frontier from `gh stack view --json` after every mutation. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the stack.** The deliverable is one linear stack of verified PRs, reviewable bottom-up on GitHub, every layer carrying its verifier verdict (swarm lanes and both thermos lenses) in the PR body or a comment. The operator reviews and lands it. The root never lands it. The report shows the two ways: `gh stack merge <pr> --yes` on the highest PR of the verified bottom-up run, which merges that PR and every unmerged PR below it as one atomic operation, or the merge box on that PR in GitHub. Auto-merge is not supported for stacked PRs. A merge queue on the base branch takes the whole stack together.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack bottom and top, a one-line verdict summary per layer (swarm and thermos), the landing command for the operator with the PR number to pass it, and anything parked or excluded with the reason.
