### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after `playbooks/babysit.md`. It runs only on an explicit request to merge, land, ship, or merge when ready. A babysit status never grants merge authority. It runs on native GitHub stacks via `gh stack` (see the `stacked-prs` skill). GitHub through `gh` is the only forge.

1. **Verify every PR independently.** Read the stack with `gh stack view --json`, or with `gh api -H 'X-GitHub-Api-Version: 2026-03-10' "repos/<owner>/<repo>/stacks?pull_request=<pr>"` when there is no checkout. Each PR gets its own verdict, not a batched approval. The review judgment comes from a reviewer who did not write the patch. An applicable prior independent verdict or GitHub bot or human review can supply that judgment. Choose the review level and reuse coverage under `skill://thermos`. Do not spawn a fresh reviewer merely because Shipping began. Confirm the relevant checks at the current head. For behavior changes, keep smoke or runtime evidence on the real surface via the matching control skill, such as `control-ui` or `control-cli`, against parent versus head. Use `skill://blast-radius` inline for a named uncertainty. Each layer returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR. Accepted blockers under the review policy make the verdict `FAIL`. Non-blocking findings can remain `PASS+NOTES`. CI green alone is not an independent verdict. If `gh stack` is unavailable or the probe `gh api -H 'X-GitHub-Api-Version: 2026-03-10' "repos/<owner>/<repo>/stacks" --silent` returns 404 (preview off), each PR stands alone or sits in a base-branch chain, and the rest of this playbook applies per PR. `gh stack view` never exits 9, so do not probe with it. `gh stack view --json` also cannot report a closed PR, so cross-check every run member with `gh pr view <pr> --json state,mergedAt` or the stacks endpoint before you call the run intact.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable. The merge target is the highest PR in that run, since `gh stack merge <pr>` also lands every unmerged PR below it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase can silently invalidate a verdict without touching a check. Before landing, compare the recorded patch-id with each run member's current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid. Inspect the delta and run relevant checks at the current head. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. When the patch changed, re-verify the affected paths and refresh that PR's verdict. Reuse review coverage for unchanged scope and choose any delta review under `skill://thermos`, not an automatic broad audit. Verify accepted fixes with targeted proof. When the patch did not change, keep the code verdict but re-run mergeability and CI at the current head. A new SHA alone does not trigger review. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Prepare the run before landing.** Fetch current trunk. If `gh stack view --json` shows `needsRebase` on any run member, or trunk moved, the single topology writer runs `gh stack sync` (or `rebase` then `push`) and the run returns to step 3. You never rebase or retarget by hand. Confirm the run's PRs are open, not draft, and mergeable per `scripts/watch-pr/watch-pr --status-only`.
5. **Land the run in one operation, pinned to the verified head.** Both paths merge the highest verified PR and every unmerged PR below it, all or nothing. You cannot merge a mid-stack PR alone, and you cannot leave a verified PR below the target unmerged. The pin path is primary. `gh stack merge` does not pin a head SHA, so a push between verdict and merge would land unverified code. Write the body `{"merge_method": "squash", "sha": "<verified head SHA of the target PR>"}` to a file and run `gh api -H 'X-GitHub-Api-Version: 2026-03-10' --method PUT repos/<owner>/<repo>/pulls/<highest-verified-pr>/merge-async --input <file>` (`merge` or `rebase` per repo convention, and `merge_action` stays `default` so a merge queue is used when the base requires one). GitHub rejects the merge if the PR head differs from `sha`. A `202` returns a `uuid`, so poll `GET repos/<owner>/<repo>/pulls/<pr>/merge-async/<uuid>` until the status is `merged`, `enqueued`, or `failed`. A `409` means a request for that PR already exists, so poll the returned `uuid` instead of resubmitting. The sha pins only the target PR, so the patch-id check of step 3 still covers the lower run members. The simple path is `gh stack merge <highest-verified-pr> --yes --squash` (or `--merge`, `--rebase`), allowed only when nothing could have been pushed since the verdict. Even then, re-read the target PR's head SHA with `gh pr view <pr> --json headRefOid -q .headRefOid` immediately before the call and compare it with the verified SHA. A mismatch sends the run back to step 3. If the base branch uses a merge queue, either path enqueues the run together, the queue picks the method, and an ejected PR ejects everything above it. Handle `gh stack merge` exit codes without retrying blind. Exit 3 means the message contained 'conflict' and no rebase is in progress, so the topology writer recovers with `gh stack rebase` then `gh stack push` and the run returns to step 3. Exit 4 can be the ten-minute poll timeout 'Merge is still in progress', and the merge may have landed or still be running, so do not retry. Recompute the frontier per step 7 first, since a retry on a request that already exists gives a 409. When the requirements are still running and the user asked for merge-when-ready, do not enable auto-merge, since GitHub does not support it for stacked PRs. Poll `scripts/watch-pr/watch-pr --status-only` as an async `bash` job (`async: true`, no `name`, `timeout: 0`) whose exit wakes you, or with a watcher subagent you `wait` on, until the run is mergeable, then merge. Or enqueue in the merge queue when the base uses one.
6. **Do not read `autoMergeRequest` as stack readiness.** It says nothing about a queue entry, a current patch verdict, or a safe contiguous run. Confirm readiness from `gh stack view --json` (`isMerged`, `isQueued`, `needsRebase`, `pr.state`) or the stacks endpoint, and from `mergeStateStatus` for the run's top PR. Say the state is unknown when GitHub cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, and re-read the frontier from `gh stack view --json` or the stacks endpoint: the ordered unmerged PRs, bottom to top, with head SHAs. GitHub retargets the next PR to trunk itself, so never hand-retarget with `gh pr edit --base`. Inspect the new bottom PR's base, head, checks, and patch-id. If part of the run is still unmerged, repeat steps 3 through 6 for it. `gh stack sync --prune` cleans merged local branches, run by the topology writer. Independent work stays outside this chain and ships on its own.
8. **Watch the landing until it merges or fails. Do not mutate the queue around it.** Use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>` only as an event wake and poll `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup` after each wake, ignoring `READY` until `mergedAt` is non-null or `state` is `MERGED`. In a merge queue, `gh stack view --json` reports `isQueued` until the group lands. Only then run step 7. Hard-fail only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE` or `CANCELLED` and blocks merge, the queue ejects a PR, or `mergeStateStatus` is `DIRTY`. `BLOCKED` or `UNSTABLE` while checks are pending or the entry is queued is not failure. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition here. Hold the watch as an async `bash` job or a watcher subagent you `wait` on, restarted after each wake, and never as a `/loop` you start yourself. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, the merge command or queue entry you used and how you confirmed it, what landed, and what the next gap needs.
